# Project Decisions

Architectural and design decisions made during development.
All agents should read this before starting work and log new decisions here.

## Media extractors: suggested filename from real title, not opaque id
**When**: 2026-08-13 18:24:18

User-reported UX bug: downloaded videos were saved as "ytdlp-{id}"/"youtube-{id}" instead of the real video title. Fixed by reading yt-dlp's "title" field (YtDlpMediaExtractor) and videoDetails.title from the already-parsed player response (YouTubeMediaExtractor), sanitized via a new shared CrossPlatformFileName.Sanitize(string?) helper (same logic HttpFileNameResolver already used privately, now reusable). Both extractors fall back to the old opaque id-based name when no title is available/parseable — never throws, matches the existing graceful-degradation contract (D3). FacebookMediaExtractor was intentionally left unchanged: its embed page doesn't reliably expose a title without an extra page fetch — flagged as a follow-up, not done in this pass.

**Impact**: JustDownload.Core/CrossPlatformFileName.cs (new public Sanitize method), JustDownload.Core/Media/YtDlp/YtDlpMediaExtractor.cs, JustDownload.Core/Media/YouTube/YouTubeMediaExtractor.cs, and their tests. Any future extractor wanting a title-based filename should call CrossPlatformFileName.Sanitize(title) with an id-based fallback, following this same pattern.

## Facebook title follow-up resolved: og:title now used for suggested filename
**When**: 2026-08-13 18:33:52

Follow-up to "Media extractors: suggested filename from real title, not opaque id" (2026-08-13), which explicitly deferred FacebookMediaExtractor because its embed page "doesn't reliably expose a title without an extra page fetch". Investigated further: Facebook's VideoInlinePlayerConfig JSON (the source of hd_src/sd_src) has no title field at all in either the fixtures or real-world extractor references (yt-dlp's own FacebookIE reads title from og:title/twitter:title meta tags or the <title> element, never from that JSON blob) — so a JSON field was never going to be an option. The embed endpoint's own <title> element is generic ("Facebook embed", confirmed in the existing facebook-embed-real.html fixture) and not the video's title, so it is deliberately NOT used as a source. Implemented: read the video title from the og:title meta tag — checked on embedHtml first (always fetched), then on pageHtml (only present when a short link was already followed to resolve the video id) — using a new OgTitleRegex, HTML-decoded via System.Net.WebUtility.HtmlDecode, then CrossPlatformFileName.Sanitize(title) with fallback to the existing facebook-{videoId} name, matching the exact pattern YouTubeMediaExtractor/YtDlpMediaExtractor already use. No extra HTTP fetch was needed — both HTML sources checked were already being fetched for hd_src/sd_src or video_id resolution. Never throws (TryGetTitle degrades to null on no match), matching D3's graceful-degradation contract.

**Impact**: JustDownload.Core/Media/Facebook/FacebookMediaExtractor.cs (pageHtml hoisted out of the short-link branch so it's available as a secondary title source; new TryGetTitle + OgTitleRegex; SuggestedFileName now sanitized-title-or-fallback). JustDownload.Tests/Media/FacebookMediaExtractorTests.cs (two new tests: title found -> sanitized title used; no og:title anywhere -> falls back to facebook-{id}). JustDownload.Tests/Fixtures/facebook-embed-with-title.html (new synthetic fixture with an og:title tag). All extractors flagged in the original entry (YouTube, yt-dlp, Facebook) now use the real-title-with-fallback pattern; no further follow-up remains from that decision.

## HLS/DASH manifest URLs in New Download dialog now detected via IMediaExtractorRegistry, gated by URL extension
**When**: 2026-08-13 19:22:24

Bug fix (Twitter/X .m3u8 sniffed by the extension, and any other host serving a sniffable .m3u8/.mpd, downloaded as raw manifest text instead of a real video): NewDownloadViewModel.DetectAsync previously only ever ran IResourceProbe's plain HTTP probe, so an HLS/DASH manifest URL was treated as if it were the video file itself — EnqueueDownloadRequest.MediaKind stayed null, and DownloadManager.cs:223 took the plain progressive HTTP-GET path, saving the playlist/manifest text verbatim.

Fix: DetectAsync now first checks the URL's file extension (.m3u8/.m3u/.mpd, case-insensitive) via a new LooksLikeMediaManifest() prefilter. Only when it matches does it call the existing IMediaExtractorRegistry.ExtractAsync (the same registry/extractors MediaVariantPickerViewModel's extension-driven quality picker already uses — HlsMediaExtractor, DashMediaExtractor, etc.) — reusing the real playlist/manifest parsing rather than duplicating it. Every other URL (the overwhelming majority pasted/typed into this dialog) never reaches the registry at all, so: (a) ordinary progressive downloads are byte-for-byte unaffected (proven by a new regression test asserting the registry is never consulted for a non-manifest URL), and (b) YouTube/Facebook/yt-dlp extractors (also registered in the same registry, priority-ordered before the catch-all) never run against a plain pasted link — they only see manifest-shaped URLs, where they cheaply decline on host mismatch before HLS/DASH's real extractor takes over.

Considered but rejected: (1) Content-Type-based detection in addition to extension — would need IResourceProbe/ResourceProbeResult changed to expose Content-Type, a bigger surface than the reported bug needs; extension-based detection alone covers the real-world case (Twitter/X CDN URLs carry .m3u8 in the path) — flagged as a follow-up if a manifest URL without a recognizable extension is ever reported. (2) Always calling the full registry for every URL (no prefilter) — rejected for being needlessly heavy (D9 "light & fast") and for risking the optional yt-dlp fallback extractor spawning/considering a subprocess on URLs that were never meant to be media at all. (3) Wiring ITosNoticeGate into this new extraction call site (its own interface doc says it must be "consulted right before extraction actually runs") — NOT done in this fix to keep the change surgical and scoped to the reported routing bug; this is a known, flagged gap: a media download can now be enqueued through the New Download dialog without the one-time ToS notice CLAUDE.md §5 calls for. Recommended as a fast follow-up.

For a detected master playlist/adaptive manifest (Variants.Count > 0), the same selection helpers the quality picker uses are reused to resolve a concrete stream URL up front (no picker UI exists in this dialog): VideoQualitySelector.Select(..., AppSettings.DefaultVideoQuality) for video, AudioQualitySelector.Select(...) for audio when present, AppSettings.DefaultContainer for the output container. This is required, not optional: JustDownload.Core/Media/Hls/HlsDownloader.cs:50-54 throws HlsExtractionException if ever given a master (not media) playlist URL directly, so routing the raw master URL through as MediaKind.Hls without pre-resolving a variant would just trade one failure mode (raw text saved) for another (download always fails).

**Impact**: JustDownload.App/ViewModels/NewDownloadViewModel.cs (new IMediaExtractorRegistry constructor dependency; DetectAsync tries media detection before the plain probe; new ApplyMediaDetection/TryDetectMediaAsync/LooksLikeMediaManifest/MediaFileName helpers; SubmitAsync sets MediaKind/MediaAudioUrl/MediaContainer and uses the resolved variant Url when a media source was detected; OnUrlChanged now also clears the stale detection). JustDownload.Tests/App/NewDownloadViewModelTests.cs (Harness gained MediaRegistry + SetMediaSource; two new tests: HLS master-playlist detection/routing, and a plain-URL regression proving the registry is never consulted). JustDownload.Tests/App/NewDownloadWindowTests.cs (constructor call site updated for the new parameter). MediaVariantPickerViewModel and the extension's EXTRACTABLE_HOSTS list were not touched — the extension-driven extract=true flow is unaffected (verified: MediaVariantPickerTests, 29/29, still green).

## Diagnostics: live/opt-in-only probes are separate console projects, not xUnit tests
**When**: 2026-08-13 20:04:41

Task 57590d08 needed a harness that hits real external sites (facebook.com, x.com, youtube.com, instagram.com) using the real DI-wired IMediaExtractor set, but must never run automatically in dotnet build/dotnet test/CI. Followed the existing JustDownload.Perf precedent: a plain console-app project (OutputType Exe, top-level Program.cs, no [Fact]/[Trait]) that IS part of JustDownload.sln and builds cleanly under `dotnet build -c Release`, but only executes when explicitly invoked via `dotnet run --project <name>`. This was chosen over an xUnit [Trait("Category","LiveSmoke")] approach because the project already has this exact pattern established (Perf), it needs no test-filter discipline from every future `dotnet test` invocation to stay silent, and a console app's stdout is a more readable diagnostic report than xUnit's test-runner output for a human reading per-extractor accept/decline/exception lines.

**Impact**: New project JustDownload.LiveSmoke (references JustDownload.Core only). Future "hits real external systems, must never run in CI" diagnostic needs should follow the same shape: a console project added to the .sln, built by default, run only via an explicit `dotnet run --project`.

## New Download dialog: detection state is replaced, never pre-cleared
**When**: 2026-08-13 20:37:04

NewDownloadViewModel.DetectAsync used to wipe _detectedMedia at the top of every pass, before any await. Clicking "Download now" moves focus off the URL TextBox, and NewDownloadWindow.OnUrlCommitted (LostFocus) fires a fresh DetectAsync in the same click — that pass wiped the already-resolved HLS source and was still awaiting the extractor when SubmitAsync read it, so the request silently degraded to a plain progressive GET of the .m3u8 (DB rows 60/62/63: media_kind NULL, 334-byte "video"). The rule is now: _detectedMedia is only ever REPLACED by the pass that produces a new verdict (ApplyMediaDetection sets it, ApplyDetection nulls it) or dropped when the URL itself changes (OnUrlChanged, which now also clears DetectionMessage so the two can't disagree). A cancelled or superseded pass leaves the previous good result intact. Paired with a guard in SubmitAsync: a LooksLikeMediaManifest URL with no _detectedMedia re-runs detection once and, if it still can't resolve, refuses the submit with a warning instead of enqueuing the manifest as a file (§5 no silent failures). Alternative considered and rejected: snapshotting detection state into the submit path or gating submit on !IsDetecting — both leave the underlying "a superseded pass can destroy good state" hazard in place for the next caller.

**Impact**: JustDownload.App/ViewModels/NewDownloadViewModel.cs (DetectAsync, ApplyDetection, SubmitAsync, OnUrlChanged). Any future async state applied by DetectAsync should follow the same replace-don't-pre-clear rule. Covered by 3 tests in JustDownload.Tests/App/NewDownloadViewModelTests.cs.

## HLS: #EXT-X-MAP initialization segment is part of the download, not metadata
**When**: 2026-08-13 21:01:31

Hands-on diagnosis of the user's "Twitter video downloads but won't play" report found M3U8Parser.ParseMedia silently ignored #EXT-X-MAP (it starts with '#' and matched no known tag, so it fell through the else-if chain). Twitter/X — and every CMAF/fragmented-MP4 HLS stream — carries the ftyp/moov boxes ONLY in that initialization segment and serves .m4s fragments that are meaningless without it. HlsDownloader therefore fetched just the fragments and HlsConcatenator produced a file starting with styp/moof; ffprobe rejects it with "trun track id unknown, no tfhd was found". Verified on the user's own machine: the app's output for the reported tweet was 851149 bytes and unplayable; prepending the 898-byte init segment to the byte-identical fragments yields a valid 69.88s H.264 file (852047 bytes, ffprobe clean), and the real DI-wired IHlsDownloader+IHlsConcatenator now produce exactly that. Design choices: (a) only the FIRST #EXT-X-MAP is kept — a second, mid-stream map re-initialises the decoder, which a pure byte-append pipeline cannot express, and appending it would corrupt the output; (b) the init segment is fetched BEFORE the parallel segment loop so an unfetchable init fails fast with HlsExtractionException rather than silently returning fragments alone (CLAUDE.md §5, no silent failures); (c) InitializationSegment was added as a defaulted positional record parameter so the single existing construction site needed no churn. Rejected: treating the init segment as a synthetic HlsSegment (it has no duration, no media sequence, and must never be AES-decrypted) and post-processing with ffmpeg (a byte prepend is exact and needs no external process).

**Impact**: JustDownload.Core/Media/Hls/M3U8Parser.cs (MapTag const, ParseMap helper), HlsMediaPlaylist.cs (new InitializationSegment property), HlsDownloader.cs (fetch + prepend to SegmentFiles, init bytes counted in TotalBytes). Any future HLS work must keep the init segment first in SegmentFiles — the concatenator is a pure ordered byte append and order is load-bearing. NOTE: #EXT-X-BYTERANGE remains unsupported for both EXT-X-MAP and media segments (pre-existing gap, not introduced here) — a playlist using byte-range addressing will still produce a wrong file. Covered by 4 tests in JustDownload.Tests/Media/{M3U8ParserTests,HlsDownloaderTests}.cs.

## Media extraction reports per-extractor outcomes; "recognised but failed" is signalled by MediaExtractionFailedException
**When**: 2026-08-13 21:17:57

Every extractor returned a bare null and MediaExtractorRegistry.ExtractAsync caught-and-continued, so a DNS failure, a yt-dlp bot challenge and "this page genuinely has no video" all collapsed into the one string "Couldn't find downloadable media at this URL." in the picker. On Sarfraz's machine the only way to recover a real reason was running yt-dlp by hand — YtDlpMediaExtractor logged its stderr at LogLevel.Debug and his logging.minimum_level is Error, so it was discarded. The reason therefore had to travel back through the return path, not the log.

TWO contract changes were weighed. (a) Change IMediaExtractor.TryExtractAsync to return a rich attempt type: cleanest on paper but touches all 6 extractors, every `return null`/`return new MediaSource` site, LiveSmoke and ~40 extractor tests. (b) Registry-level only: cannot express "recognised the URL but failed" at all, because that case currently returns null exactly like a decline. CHOSEN: a middle route — the registry's return type changes (IMediaExtractorRegistry.ExtractAsync now returns a non-null MediaExtractionResult { Source, Attempts }), while IMediaExtractor's signature is untouched; an extractor that recognised the URL but could not extract throws the new sealed MediaExtractionFailedException carrying the reason. That keeps declines cheap and silent (return null, unchanged for 5 of 6 extractors), needs no churn in extractors that already behave correctly, and is not exceptions-as-control-flow: it IS a failure.

Vocabulary: MediaExtractionOutcome { Accepted, Declined, Failed, NetworkFailure }. NetworkFailure is its own category because HttpRequestException / SocketException / a non-user-cancelled OperationCanceledException (an extractor's internal timeout) say nothing about whether media exists — reporting them as "no media found" is what sent the user hunting for a broken extractor instead of his NextDNS resolver null-routing facebook.com. Detection walks InnerException, since a DNS failure arrives as HttpRequestException wrapping SocketException. Routing is deliberately UNCHANGED: first non-null still wins, priority order untouched, one failing extractor still does not abort the chain.

MediaExtractionAttempt has a private constructor and four static factories, so Reason is non-null exactly for Failed/NetworkFailure and null otherwise — the illegal pairings are unrepresentable rather than validated. Both factories run the reason through ExtractionReasonSanitizer, which collapses whitespace, strips the query/fragment off every embedded URL (where signatures/tokens/cookies live) and truncates at 160 chars. Sanitizing at construction, not at display, means an unredacted reason can never exist in an attempt at all (CLAUDE.md §5) — including in the log line the registry writes for it.

D5 is preserved: Core produces structured outcomes only. The wording lives in JustDownload.App/Formatting/MediaExtractionMessage.cs, which both dialogs call — network failure wins over everything, then attributed extractor reasons (max 2), then the original generic string when every extractor merely declined.

YtDlpMediaExtractor's two non-failure gates (master toggle off, yt-dlp not provisioned) still decline silently. Its four real failure modes — non-zero exit, launch failure, unreadable JSON, no usable format — now throw with the reason; for a non-zero exit that is the LAST "ERROR: …" line of stderr with the prefix stripped, which is where yt-dlp puts the actual cause (bot challenge, HTTP 429, missing JS runtime). Deliberately NOT special-cased: "Unsupported URL" is reported as a failure like any other rather than silently downgraded to a decline — a magic-string test risked mis-classifying, and "yt-dlp: Unsupported URL" is more useful to the user than the generic message anyway.

**Impact**: NEW in JustDownload.Core/Media/Extraction/: MediaExtractionOutcome.cs, MediaExtractionAttempt.cs, MediaExtractionResult.cs, MediaExtractionFailedException.cs, ExtractionReasonSanitizer.cs. CHANGED: IMediaExtractorRegistry.ExtractAsync now returns Task<MediaExtractionResult> (never null) — every call site reads .Source; MediaExtractorRegistry classifies each attempt; IMediaExtractor's doc contract now names MediaExtractionFailedException; YtDlpMediaExtractor throws instead of returning null for its four failure modes. NEW JustDownload.App/Formatting/MediaExtractionMessage.cs; MediaVariantPickerViewModel.LoadCoreAsync and NewDownloadViewModel (DetectAsync / TryDetectMediaAsync / SubmitAsync's manifest refusal, via the new _mediaFailure field) use it. JustDownload.LiveSmoke/Program.cs handles the new exception. ANY FUTURE EXTRACTOR: return null only for "not mine"; throw MediaExtractionFailedException with a reason whenever you recognised the URL and could not deliver — returning null there is now a silent failure. Tests: MediaExtractorRegistryTests, YtDlpMediaExtractorTests, MediaVariantPickerTests, NewDownloadViewModelTests, DashLoopbackTests, ExtractorCorpusTests, TestFixturesTests.
