Architectural and design decisions made during development.

## Media picker: a zero-variant source is downloadable via a synthetic, unlisted variant (TASK-239)
**When**: 2026-08-14 08:02:37

`MediaVariantPickerViewModel.ConfirmAsync` builds the enqueue request exclusively from `SelectedVariant.Variant.Id`, and `SelectedVariant` was only ever assigned when `source.Variants.Count > 0`. Every zero-variant source — Facebook (`Kind=Progressive`), the progressive catch-all extractor, an HLS *media* (non-master) playlist, Twitter/X — therefore left `CanConfirm` false and the Download button (`MediaVariantPickerWindow.axaml:77`, `IsEnabled="{Binding CanConfirm}"`) permanently greyed out. The old `else if (Kind == Progressive)` branch only set a message, so the direct-download path was structurally dead: `_source.Url` was never used as a download URL anywhere in the file. Sarfraz hit this live on a facebook.com/reel (message shown, button dead) and on x.com (no message at all, button dead).

Fix (JustDownload.App/ViewModels/MediaVariantPickerViewModel.cs, LoadCoreAsync): when `source.Variants.Count == 0`, synthesise ONE `VariantOption(new VideoVariant(source.Url.ToString(), 0), "Original")` and assign it to `SelectedVariant`. This mirrors `NewDownloadViewModel.ApplyMediaDetection`'s existing `chosenVideo is not null ? new Uri(chosenVideo.Id) : source.Url` fallback and reuses `ConfirmAsync` unchanged — it still passes `MediaKind = Kind`, so `DownloadManager` keeps routing HLS/DASH through the segment/concat/mux pipeline (`DownloadManager.cs:223`) and Progressive through the plain HTTP transport. No second enqueue path, no I/O in the view-model (CLAUDE.md §6), no master-playlist detection (a zero-variant `Kind=Hls` source from `HlsMediaExtractor` is always a media playlist; `HlsDownloader.cs:62-65` throws only for a master, and Twitter's master case is being fixed in the extractor separately).

The synthetic option is deliberately NOT added to the `Variants` collection: `HasVariants` stays false, so the Quality and Container ComboBoxes stay hidden rather than showing a single meaningless entry. The message is kept and differentiated by kind — Progressive keeps "This is a direct download — no quality options."; anything else (Hls/Dash) gets "Single stream — no quality options.", so the x.com case is no longer silent.

Secondary fix in the same method: `HasVariants`/`HasAudio`/`CanConfirm` are plain computed properties over collections whose `Clear()` announces nothing, and they were re-raised only on the success path. The three `OnPropertyChanged` calls moved into the `finally` block so every exit path (early "nothing found" return, the catch, success) announces them — previously a failed load after a successful one left the Quality ComboBox on screen, empty.

Known pre-existing wart, NOT changed (out of scope, and it already affects the existing yt-dlp progressive path): `MediaFileName` names every picker download by the chosen CONTAINER extension (default `.mkv`), but `DownloadManager` only remuxes non-Progressive kinds — so a direct `.mp4` download is saved as `<name>.mkv` with unremuxed mp4 bytes. Worth a follow-up: use the source URL's own extension when `Kind == Progressive`.

**Impact**: JustDownload.App/ViewModels/MediaVariantPickerViewModel.cs (class XML doc, LoadCoreAsync else-branch, OnPropertyChanged trio moved to finally). JustDownload.Tests/App/MediaVariantPickerTests.cs (existing LoadAsync_Progressive_ShowsDirectDownloadMessage extended with a CanConfirm==true assertion — its old expectation of a dead button was the bug frozen in place; 4 new tests). No XAML change: the Download button binding was already correct. JustDownload.Core untouched; TwitterMediaExtractor and NewDownloadViewModel untouched.

## Twitter/X HLS: master playlist now enumerates real quality variants
**When**: 2026-08-14 08:09:46

TwitterMediaExtractor's HLS branch (TwitterMediaExtractor.cs) always returned Variants = [] for the HLS master playlist URL resolved from the syndication API. Because MediaExtractorRegistry accepts the first non-null result regardless of variant count, this silently pre-empted yt-dlp (Priority=int.MaxValue) — which used to return the same x.com URL as Hls with 4 real quality variants — from ever running. Fix: TryBuildFromJsonAsync (renamed from the sync TryBuildFromJson) now fetches the resolved HLS URL via the new TryFetchHlsVariantsAsync helper and, when M3U8Parser.IsMaster(text) is true, parses it with M3U8Parser.ParseMaster exactly like HlsMediaExtractor.cs:71-86 does, populating Variants from HlsMasterPlaylist.Variants. Graceful-degradation guarantee preserved: a fetch exception (HttpRequestException/IOException/InvalidOperationException), a non-2xx status, a body without #EXTM3U, or an actual media (non-master) playlist all fall back to Variants = [] — never throws, never returns null, the master/media URL itself remains a valid single-stream download via the picker's existing zero-variant fallback. Only OperationCanceledException still propagates, matching the class's existing contract. Priority stays 91 (unchanged) — re-ordering extractor precedence was explicitly out of scope for this fix.

**Impact**: JustDownload.Core/Media/Twitter/TwitterMediaExtractor.cs (new using JustDownload.Core.Media.Hls; TryBuildFromJson -> async TryBuildFromJsonAsync taking MediaRequest+CancellationToken; new private TryFetchHlsVariantsAsync helper; two new [LoggerMessage] partials EventId 5/6). No change to MP4 branch, syndication JSON parsing, token logic, or Priority.

## yt-dlp reliability: provision Deno as yt-dlp's JS-challenge-solver runtime
**When**: 2026-08-14 08:33:00

Verified against yt-dlp's own EJS wiki page: to download from YouTube, yt-dlp needs to solve JS challenges, and "only deno is enabled by default" among the runtimes it supports — without one, yt-dlp silently drops the `web` client and loses signature-protected formats, very likely a major cause of Sarfraz's "Sign in to confirm you're not a bot" failures. Deno is MIT-licensed (verified via GitHub API `license.spdx_id` before pinning, per CLAUDE.md §4) and ships one executable zipped per platform — an archive-based provisioner mirroring FfmpegProvisioner's pattern (download → SHA-256 verify → extract), not yt-dlp's single-file provisioner, since Deno's zip has no `bin/` folder (the executable sits at the archive root).

Pinned to Deno v2.9.5 (2026-08-14): win-x64, linux-x64, osx-x64, osx-arm64 all verified by independently downloading each archive and computing its own SHA-256 with Python hashlib, then cross-checking against Deno's published per-asset `<asset>.zip.sha256sum` sibling file (Windows format is PowerShell Get-FileHash output, Unix format is plain `sha256sum`) — every hash matched. win-arm64 and linux-arm64 are NOT pinned (out of scope for this pass, documented as a gap in DenoManifest's doc comment).

`YtDlpMediaExtractor` now injects `IDenoLocator` and appends `--js-runtimes deno:<path>` explicitly to every probe (base + cookie retry) when Deno is located — never relying on yt-dlp's own "same folder as yt-dlp.exe" auto-detection (Windows-only, undocumented-fragile). When Deno isn't located, nothing changes: purely additive, non-regressing. Provisioning is wired into the existing "Download yt-dlp" button in `VideoSettingsViewModel` (one click provisions both, sequentially) rather than a second button — Deno is a dependency of yt-dlp working well, not a separate feature (D3: provisioning stays an explicit user action). A Deno provisioning failure never fails the yt-dlp result; it's surfaced via the new non-fatal `DenoWarning` property instead (CLAUDE.md §5: no silent failures).

**Impact**: New: JustDownload.Core/Media/{DenoException,DenoInfo,DenoOptions,DenoDownloadSource,DenoManifest,IDenoLocator,DenoLocator,IDenoProvisioner,DenoProvisioner}.cs. Changed: JustDownload.Core/Media/YtDlp/YtDlpMediaExtractor.cs (new IDenoLocator ctor param, --js-runtimes wiring), JustDownload.Core/ServiceCollectionExtensions.cs (Deno DI registration + vendor-dir default, mirroring ffmpeg/yt-dlp), JustDownload.App/ViewModels/Settings/VideoSettingsViewModel.cs (new IDenoProvisioner + ILogger ctor params, DenoWarning property, ProvisionDenoAsync), JustDownload.App/ViewModels/Settings/SettingsViewModel.cs (threads the two new deps through to VideoSettingsViewModel), JustDownload.App/Views/SettingsWindow.axaml (DenoWarning TextBlock, no new button). Tests: new DenoManifestTests.cs, DenoProvisionerTests.cs; extended YtDlpMediaExtractorTests.cs (3 new --js-runtimes tests), SettingsViewModelTests.cs (2 new Deno-provisioning tests + all existing VideoSettingsViewModel construction sites updated), SettingsWindowTests.cs, VendorDirectoryDefaultsTests.cs (DenoOptions default dir test).

## yt-dlp: pinned release channel switched from stable to nightly
**When**: 2026-08-14 08:33:11

The previously-pinned stable tag `2026.06.09` (later found to actually need refreshing further) was stale: Instagram's logged-in-extraction fix (commit `1f1101d`, merged 2026-07-21) is not in ANY stable release — latest stable at research time was `2026.07.04` (confirmed via `https://api.github.com/repos/yt-dlp/yt-dlp/releases`) — only in nightly/master. `yt-dlp/yt-dlp-nightly-builds` publishes the same asset names and a `SHA2-256SUMS` file per release as stable does, so `YtDlpManifest.ReleaseUrl` now points there instead of `yt-dlp/yt-dlp`, keeping the exact same static-pinned-hash-in-source approach (CLAUDE.md §4) — this is a channel switch only, not a move to a dynamic "always fetch latest" resolver, which would trade away the integrity-pinning guarantee for a bigger architecture change Sarfraz hasn't signed off on.

Pinned tag `2026.08.04.234419`, fetched 2026-08-14 from `https://api.github.com/repos/yt-dlp/yt-dlp-nightly-builds/releases/latest`. All six hashes (win-x64, win-arm64, linux-x64, linux-arm64, osx-x64/arm64 sharing the one `yt-dlp_macos` universal binary) were copied verbatim from that release's `SHA2-256SUMS` asset, not reused from the old stable pin. Nightly builds land far more often than stable (roughly daily vs. weekly), so this manifest will go stale faster than before — documented in the class's doc comment as an accepted tradeoff for YouTube/Instagram reliability, not a bug; refresh again once this pin is superseded.

**Impact**: JustDownload.Core/Media/YtDlpManifest.cs (ReleaseUrl base repo, ReleaseTag, all six Sha256 values, updated doc comment on refresh cadence). No structural/test change — JustDownload.Tests/Media/YtDlpManifestTests.cs already passes unchanged since it only asserts generic invariants (HTTPS, 64-hex-char hash, RID coverage), not specific hash/tag values.

## yt-dlp cookie retry: narrowed to genuine login-required errors, Firefox-first, player_client workaround
**When**: 2026-08-14 (session following the Deno/nightly-pin work above)

`YtDlpMediaExtractor`'s cookie-retry gate (`IsBotDetectionReason`) matched a broad substring set — the generic "confirm you're not a bot" wall, bare "bot", bare "cookies", HTTP 429, "too many requests" — and retried with cookies on all of them. Per yt-dlp issue #17389 (opened 2026-08-07, `high-priority`+`site-bug`, still open): sending `--cookies-from-browser` on a request that would otherwise succeed on the generic bot-challenge message produces a NEW failure, `ERROR: [youtube] ...: The page needs to be reloaded.` — the reporter confirmed "If I do not pass a browser cookie, however, then everything downloads fine." Root cause per maintainer `gamer191`: cookies switch yt-dlp into the `tv_downgraded` client, whose JS signature the challenge-solver can't yet handle. The old broad matching was exactly the counterproductive case #17389 documents. Renamed to `RequiresLoginReason` and narrowed to specific login-required phrases only: `"private video"`, `"sign in to confirm your age"`, `"members-only"`, `"sign in to view this content"`, `"login required"`, `"registered users only"` — the generic bot wall and 429/rate-limit no longer trigger a retry at all (a guest-session rate limit isn't fixed by cookies, only by waiting). Kept deliberately conservative: false negatives (missing a real login-gated case) are safer than false positives (which is what broke things per #17389).

`BrowserCookieCandidates` reordered to Firefox-first (`["firefox", "chrome", "edge", "brave", "opera"]`, was chrome-first). Per yt-dlp maintainer `bashonly` (issue #15401, 2025-12-29/30): Chromium browsers on Windows hit an unresolved sqlite cookie-DB lock (issue #7271, open since 2023) and a DPAPI-decryption dead end requiring admin rights — "no plan" to fix otherwise, with removing Windows Chromium-cookie support floated entirely. yt-dlp's own FAQ: "this method reportedly works best with Firefox." Detection logic (`RealBrowserCookieStoreExists`) unchanged — only the probe order moved.

Whenever cookie args go out (explicit `--cookies`/`--cookies-from-browser` setting OR auto-detected), `--extractor-args "youtube:player_client=default,web_embedded"` is now appended alongside them as a fixed pair — the maintainer-pinned #17389 workaround, confirmed working by the reporter same-day. Accepted caveat (documented, not branched around): `web_embedded` breaks live-stream downloads after ~4 minutes (403 loop) but works fine for VOD, the app's primary use case.

**Impact**: JustDownload.Core/Media/YtDlp/YtDlpMediaExtractor.cs (`IsBotDetectionReason` renamed to `RequiresLoginReason` with narrowed phrase matching; `BrowserCookieCandidates` reordered; cookie retry argv now appends the `--extractor-args` pair alongside cookies in the single shared code path so both the explicit-setting and auto-detected branches get it; doc comments and `[LoggerMessage]` text updated from "bot-detection" to "login-required" terminology). JustDownload.Tests/Media/YtDlpMediaExtractorTests.cs (8 existing tests renamed/updated from generic bot-wall or 429 trigger messages to genuine login-required messages, since those no longer trigger a retry under the new gate; 8 new tests: generic-bot-wall-no-retry, login-required-does-retry, 429-no-retry, extractor-args-appended for both the explicit and auto-detected cookie paths, and Firefox-preferred-over-chrome). Deno `--js-runtimes` wiring, explicit-setting precedence, and the auto-detected-retry-failure-swallowing asymmetry were all left untouched (out of scope, already correct).

## Fix: yt-dlp/Deno provisioner silently skipped upgrades (stale-binary bug)
**When**: 2026-08-14 09:11:37

Root-caused why two prior session commits (nightly yt-dlp pin to 2026.08.04.234419 for Instagram's GraphQL fix, and Deno auto-provisioning) never took effect on Sarfraz's machine: YtDlpProvisioner.EnsureAsync/DenoProvisioner.EnsureAsync (JustDownload.Core/Media/YtDlpProvisioner.cs, DenoProvisioner.cs) returned ANY existing located binary immediately, never comparing its version against the pinned manifest — so a yt-dlp already on disk from before the pin change (2026.06.09) was silently kept forever, "Download yt-dlp" in Settings was a no-op. Compounded by YtDlpLocator/DenoLocator caching their LocateAsync() result forever in a private field for the lifetime of the DI singleton, so even a correct re-download wouldn't reach an already-running consumer (e.g. YtDlpMediaExtractor) without a restart.

Fix: EnsureAsync now compares the located binary's version against the pinned manifest version, but ONLY auto-upgrades a binary that lives at OUR OWN vendor-directory path (Path.Combine(vendorDir, ExecutableName)) — a user-configured YtDlpPath/DenoPath or a PATH-resolved binary is never touched, respecting D3's "never evade user configuration" posture. Added IYtDlpLocator.Invalidate()/IDenoLocator.Invalidate() (clears the cached field under the existing _gate lock) called (a) right after detecting a version mismatch, so the "another caller may have provisioned while we waited" recheck sees the real file, and (b) right after replacing the binary on disk, so self-validation and every other consumer sharing the singleton locator picks up the new version within the same process — no app restart needed. Deno's manifest Version carries a "v" release-tag prefix (v2.9.5) while DenoLocator.ParseVersion reports the plain "2.9.5" from `deno --version`'s banner, so DenoProvisioner normalizes the prefix before comparing.

Live-verified on Sarfraz's real machine (2026-08-14) via a throwaway harness (JustDownload.Core DI container, real VendorDirectory pointed at %AppData%\JustDownload\yt-dlp and \deno, temp DB dir): BEFORE yt-dlp=2026.06.09, deno=2.9.5 (already current). AFTER EnsureAsync(): yt-dlp upgraded in place to 2026.08.04.234419 (file replaced, checksum-verified), deno left untouched (already matched pinned version — proves the "no unnecessary re-download" path also works for real). In-process cache invalidation confirmed: LocateAsync() via the same singleton locator immediately after EnsureAsync() returned the fresh version, not stale. Real extraction test against Sarfraz's exact reported URLs: Instagram (https://www.instagram.com/reels/Dbnng9EBBfr/) now ACCEPTED (SeparateStreams, 5 variants, 1 audio variant) — the Instagram GraphQL fix is now actually reaching the app. YouTube (https://www.youtube.com/watch?v=HH6QqWyXJu8) STILL fails, but now with yt-dlp's own specific "Sign in to confirm you're not a bot" message (progress — this is yt-dlp actually running with cookie/JS-runtime support and being challenged, not a stale/broken binary) — YouTube's bot wall is NOT solved by this fix alone and needs separate follow-up (likely real cookies-from-browser or PO token support).

**Impact**: JustDownload.Core/Media/YtDlpProvisioner.cs, DenoProvisioner.cs, IYtDlpLocator.cs, IDenoLocator.cs, YtDlpLocator.cs, DenoLocator.cs, and their tests. Any future consumer of IYtDlpLocator/IDenoLocator implementing the interface directly (not via NSubstitute) must now also implement Invalidate().

## Twitter/X HLS "no audio" bug: fixed the parser/extractor/coordinator gap for alternate-audio renditions
**When**: 2026-08-14 09:24:37

Root-cause: a three-layer gap, not one bug. (1) Parser gap — M3U8Parser.ParseMaster never read #EXT-X-MEDIA:TYPE=AUDIO (RFC 8216 §4.3.4.1); HlsMasterPlaylist carried no audio-rendition data at all. (2) Extractor gap — TwitterMediaExtractor.TryFetchHlsVariantsAsync only mapped master.Variants into VideoVariant and always set AudioVariants=[] on the returned MediaSource, even though MediaSource.AudioVariants' own doc comment already promised "HLS alternate audio" support. (3) Download/mux gap — MediaDownloadCoordinator.DownloadHlsAsync (MediaKind.Hls path) completely ignored MediaDownloadRequest.AudioUrl; even a populated AudioVariants selection from the picker had nowhere to go, since only the single video HLS stream was ever downloaded/concatenated for Hls kind. The picker VM (MediaVariantPickerViewModel) and quick-add flow (NewDownloadViewModel.ApplyMediaDetection) were both already fully generic over source.AudioVariants — no changes needed there.

Real-world verification (no live x.com access from this sandbox — same limitation as the prior Twitter HLS task): web research found two authentic captured video.twimg.com master.m3u8 examples (2022/2023 CDN captures) where every #EXT-X-STREAM-INF declares combined CODECS="mp4a.40.2,avc1..." with NO separate #EXT-X-MEDIA:TYPE=AUDIO group — the common Twitter shape has audio muxed into each variant's own fMP4 segments, so for that shape AudioVariants correctly stays empty and nothing changes. However yt-dlp's own twitter.py (verified via deepwiki) contains dedicated handling for "hls-audio-<bitrate>" format IDs coming from its generic HLS extractor, meaning some real Twitter HLS masters DO carry a genuine alternate-audio group. Given this is genuinely mixed/uncertain without a live sample, the fix implements full RFC-correct EXT-X-MEDIA:TYPE=AUDIO support end-to-end (parse -> extractor -> download+mux) rather than guessing which case is real — when absent, behavior is provably unchanged (regression test with the authentic no-audio-group fixture asserts AudioVariants stays empty); when present, audio is now selected, downloaded, and muxed correctly.

Deliberately scoped to Twitter for the extractor change (surgical, matches the reported bug) but the parser (M3U8Parser) and coordinator (MediaDownloadCoordinator) changes are extractor-agnostic infrastructure — HlsMediaExtractor (generic .m3u8 URLs) has the identical latent AudioVariants=[] gap and was NOT touched; flagged as a follow-up, not fixed here (out of scope for this bug report).

**Impact**: JustDownload.Core/Media/Hls/HlsVariant.cs (new HlsAudioRendition record; HlsMasterPlaylist gains AudioRenditions). JustDownload.Core/Media/Hls/M3U8Parser.cs (new MediaTag const, EXT-X-MEDIA:TYPE=AUDIO parsing in ParseMaster, new TryParseAudioRendition helper — skips entries with no URI, since those mean audio is muxed into the video segments, not a separate downloadable stream). JustDownload.Core/Media/Twitter/TwitterMediaExtractor.cs (TryFetchHlsVariantsAsync now returns (Variants, AudioVariants) tuple; HLS branch populates MediaSource.AudioVariants instead of always []). JustDownload.Core/Media/MediaDownloadCoordinator.cs (DownloadHlsAsync branches on request.AudioUrl; new DownloadHlsWithAlternateAudioAsync downloads+concatenates both HLS media playlists into video.stream/audio.stream then muxes via IMediaMuxer, mirroring the existing DownloadDashAsync/DownloadSeparateStreamsAsync pattern exactly — no new abstraction invented). JustDownload.Core/Media/IMediaDownloadCoordinator.cs (AudioUrl doc comment corrected — it is no longer "null (HLS)" unconditionally). Tests: JustDownload.Tests/Media/M3U8ParserTests.cs (+4), JustDownload.Tests/Media/TwitterMediaExtractorTests.cs (+2, including a fixture shaped like a real captured Twitter master playlist), JustDownload.Tests/Media/MediaDownloadCoordinatorTests.cs (+2). dotnet build -c Release: 0 warnings/0 errors. Targeted dotnet test (Media + picker + NewDownloadViewModel + DownloadManager namespaces): 389/389 passed. Full suite and dotnet format NOT run (standing instruction — on request only).
